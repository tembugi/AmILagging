# Am I Lagging?

This addon's spec. The shared rules in `../CLAUDE.md` come first: they hold every rule that isn't this addon's own and win on any conflict.

@../CLAUDE.md

A bag-slot-sized block on the bottom bar, in a bar of its own, that always shows the framerate and the world latency, numbers the game menu button shows only in its tooltip. It moves with the micro menu, and players can put it anywhere in Edit Mode. Agreed with the user.

- Name "Am I Lagging?" (title case; `ADDON_TITLE`, also the tooltip title). Folder, repo and packages `AmILagging`: "?" doesn't belong in file names. CurseForge project ID 1720989. Renamed from "Performance Block": the name says what the player wants to know; the search words (fps, latency, ping) go in the summary, since the name has none. `## Category: Performance` (the addon list groups by it and its search box matches it). MIT license, like Just the Trees (the user's choice).
- The package ships `AmILagging_Camelot.toc` as an exact copy of `AmILagging.toc` (a test checks it); keep both, never drop the copy. Versions 0.8.0 to 1.1.2 shipped only a `_Camelot` TOC, which the game reads before the plain one: a player who unzips an update over such a folder gets the stale file replaced, where without the copy the game would keep reading the old TOC (old version in the addon list, out of date at the next `## Interface`). CurseForge marks files with both TOCs compatible. Nothing else from older versions can interfere: none had SavedVariables, all loaded only `AmILagging.lua`, and 1.1.4's extra files (`AGENTS.md`, `CLAUDE.md`, `CHANGES.txt`, `Logo/`) are never loaded.

## Look
- A bar of its own between the micro menu and the bags bar: one slot in the game's bar frame art, joined to the micro menu where the bags bar hung, with the bags bar joined to it the same way. The user's choice: the block no longer disappears with the bags bar (gamepad interface, addons that hide the bags bar); for a while it was the bags bar's first slot. Inside the slot frame, a pitch black, fully opaque face (the game's empty-slot background was see-through; the user chose solid black), no empty-slot picture or background art.
- Part of the whole, not pixel-matched: the art and size are read at login and after Edit Mode from the frames around it, Blizzard's XML values only as fallbacks (also when a frame reports no size yet): the bar frame art and its reach past the slot from `BagsBar.BorderArt`, how far the micro menu's frame art reaches past its right end from `MicroMenu.BorderArt`, the slot size and plain gray frame art from `CharacterReagentBag0Slot` (regular bag slots wear a gold frame, which made the block stand out). Scale: the bags bar's (its Edit Mode Size) times the block's own Size setting (see Floating); strata and frame level: the bags bar's.
- Numbers only, no labels: FPS on top in white, world latency below in its color, both 15 px, centered horizontally on the slot frame art. Between them a line across the frame art's center (32 px wide, fading at both ends), colored by home latency with the same green/yellow/red rule (the user's choice after trying it in game; it was gold before).
- The font's figures are old style (6 and 8 rise; 3, 4, 5, 7 and 9 drop), so each number is placed by the band from its highest to its lowest possible figure (em ratios measured from Skurri in game), centered in its half of the slot: the same gap to the line as to the slot's gray inner edge, whatever the digits. No digit may touch the line or the border (the user asked for airiness).
- The font is the game's heavy number font, read from `NumberFont_Outline_Huge` (Skurri for Latin alphabets) with a normal outline, one text line per number; `STANDARD_TEXT_FONT` if that font object is missing. The user wants a font built into the game, not a bundled one, and no faux-bold (drawing copies was rejected as hacky).
- World latency only on the face: it is the delay felt in combat and movement. Home latency (chat, mail, auction house) is in the tooltip. Readability at true size (45 px) decided it, after it was explained to the user.
- A number wider than the slot less a 6.5 px margin each side (four-digit latency) shrinks to fit.
- Only the latency number changes color, by the game menu button's rule: green up to 300 ms, yellow over 300, red over 600. FPS stays white. (The game menu button colors by the worse of home and world; the block colors the number it shows.)
- The numbers update once a second while the block is on screen; a number that didn't change is left alone.
- Tooltip: the title, an empty line (as the game menu tooltip has), the game's own framerate and latency lines, FPS first to match the face (`MAINMENUBAR_FPS_LABEL`, then `MAINMENUBAR_LATENCY_LABEL` with home and world), then `v<VERSION>`. Under the framerate, "Limited by: CPU" or "Limited by: GPU" from `IsCpuBound()`, as the game's Ctrl+R counter tells it; left out when it returns nil. The game can't report GPU load; this line is what it offers (the user chose it). It stays current while open through the block's `UpdateTooltip`, which the game's tooltip calls on its own timer, as the game menu tooltip does.

## Chat and errors
- Chat only when something stopped working: no login line, no slash command, no lag warning (the user's choice).
- At login the addon checks the piece it can't do without, the micro menu it stands by. If it is missing, it says so in chat and does nothing else.
- Making room runs inside the game's own code, right after Blizzard moves or resizes a frame, so every hook and callback runs through `Guarded` (`xpcall` with the game's `CallErrorHandler`): an error never breaks the code that called it. The first error is reported through the game's error handler and said once in chat; then the addon puts the bar back the way the game set it (block hidden, no moves, no stretch) and keeps it so until /reload; if even that fails, it leaves the bar alone.
- If reading the numbers fails, the error is reported once, the numbers are cleared (old numbers would mislead), the updates stop and chat says so.

## Making room
Agreed with the user. The addon makes room for itself, and removing it leaves no trace.
- The block is its own frame, a child of UIParent (it hides with the interface, Alt+Z), anchored to `MicroMenuContainer` exactly as Blizzard anchored the bags bar there (point, the micro menu's point and the offsets, read from the bags bar's own anchor). When the bags bar hangs elsewhere, the block joins the micro menu as Blizzard's layout joins the bags (`BAGS_ANCHOR_*` from Camelot's preset constants). It joins no Blizzard list, so Blizzard's bags bar layout runs clean.
- The bags bar, when it hangs off the micro menu's right side, moves right to join the block as it joined the micro menu, with the same overlap of frame art: it stands the join plus the block's reach less the micro menu's reach after the block. A bags bar hung elsewhere is left where it is.
- The block stays when the bags bar is hidden, however it was hidden. Without the micro menu on screen (shown, with every frame above it up to UIParent shown: another addon may hide it by parenting it to a hidden frame), as when another addon replaces the game's bars, the block floats (see Floating).
- Gamepad interface (`C_InputInterfaceStyle`): the game hides the row (micro menu, bags bar, action bar). The block stands on its own, centered on the screen, between the XP bar's top and the bottom of the gamepad buttons' frame (`GamepadMainActionBarFrame`), where the user marked it on a screenshot; without that frame, just above the XP bar. Nothing moves there. The switch is followed through `INPUT_DEVICE_INTERFACE_TRANSITION` and the micro menu's, gamepad frame's and XP bar's `OnShow`/`OnHide`; the XP bar is watched from login for where it stands.
- Recentering: an addon can't add an Edit Mode system (a fixed game list; layouts saved on the server), and in Camelot the row sits at a fixed offset (`MICRO_MENU_ANCHOR_OFFSET_X`), so nothing in Blizzard's layout recenters a wider row. While the block is in its slot and the micro menu where Blizzard's layout puts it, the whole row moves left by half the growth (the slot and the join to the bags, at the bags bar's scale, in UIParent units). What the row hangs off depends on the layout (in a saved layout the action bar hangs off the micro menu; Edit Mode places bars in their default position on the screen itself), so the addon follows the anchor chains of `MainActionBar` and `MicroMenuContainer` to the frames that hang off the screen and moves each such root once. A micro menu the player placed stays where they dropped it, and the row grows to the right (the stacked bars, the XP bar stretch and the bags bar move as below; only the roots don't). The action bar is part of the row only while in its default position (Edit Mode's `IsInDefaultPosition`): a player who moved it took it, and the bars Blizzard stacks on it, out of the row, so none of them move or stretch (up to 1.2.1 a moved action bar was nudged half a slot).
- The bars above the row come from Blizzard's list of bottom bars (`EditModeUtil:GetBottomActionBars()`, without `MainActionBar`): the XP bars, the action bars stacked above them (`MultiBarBottomLeft`, `MultiBarBottomRight`, `StanceBar`, `PetActionBar`, `PossessActionBar`) and the vehicle exit button. Camelot stacks them on `MainActionBar` by their left edge (`ACTION_BARS_RELATIVE_TO_BASE_POSITIONING`), so they move with the row and line up with its left end. Only bars anchored to `MainActionBar` are touched; a bar the player moved elsewhere is left as it is.
  - The XP bar containers (the bars with `ResizeContainerBars`, `UpdateDividers` and `GetExpectedSegments`) stretch by the row's growth to reach its right end: `SetWidth` and Blizzard's own `ResizeContainerBars`, as its Size setting does, and the tick marks Blizzard placed are spread evenly again with their own `SetPoint` (the container's child frames hung by `LEFT` on its `LEFT`). Never call `UpdateDividers`: it releases and acquires the marks from Blizzard's frame pool, whose counters are secure values; called from the addon (up to 1.5.0) it tainted them, Blizzard's code read them tainted (taint log level 4), and with taint logging on Blizzard's code and wrappers threw "attempt to call a nil value" only while the addon was enabled. `ResizeContainerBars` only sets sizes and wrote nothing tainted in that log. `hooksecurefunc`s on their `SetSize`/`SetWidth` keep the stretch when Blizzard resizes them, and on `SetPoint` notice them moving onto or off the row. A container is resized only when its width has to change.
  - The other bars are fixed buttons and can't stretch, so they move right by half the growth to stay centered over the row.
  - They are watched from login: Edit Mode first parks them at the screen's top left and stacks them on the action bar a moment later.
- Moves are applied in `hooksecurefunc`s on `SetPoint` and `ClearAllPoints` of each moved frame, each time Blizzard anchors it, from the points Blizzard set. Each point is remembered and moved on its own: Edit Mode gives a frame snapped to two others a second point, and sets the two one after the other. The moves use Edit Mode's plain `SetPointBase`: its replaced `SetPoint` and `ClearAllPoints` also change snapping and flag anchor changes, which the addon must not do, and the plain original never reaches the addon's own hooks. A point is set only when its offset has to change, and remembered as moved only once the move worked. Offsets and widths go through effective scales, since frames can be scaled apart.
- Edit Mode drags: the client moves a dragged bar itself (`StartMoving`, `StopMovingOrSizing`), replacing its points without `SetPoint`, so the hooks don't see it; after the drop Edit Mode sets the point again on UIParent and only then marks the bar as moved (`UpdateSystemAnchorInfo`). So a bar in the player's hand (Edit Mode's `isDragging`) is never moved; before each move the remembered points are checked against the frame's own (a point the frame no longer has is forgotten, never put back); and the layout runs again once Edit Mode is done with a moved bar (`OnSystemPositionChange` hooked). Earlier versions could put back a point the game had replaced, nudge a dropped micro menu or bags bar, and move a bar in the player's hand; the user saw Edit Mode lose the micro menu's edges while dragging it ("attempt to perform arithmetic on local 'left'" at EditModeSystemTemplates.lua:607), proven possible in the stand-in, not proven to be that error's cause.
- The bags bar is watched from login like the other moved frames (`SetPoint`/`ClearAllPoints` hooks): where Blizzard hangs it decides where the block stands. `OnShow`/`OnHide` also run when a frame above a hooked frame is shown or hidden; hiding the whole interface (Alt+Z) hides only UIParent and changes nothing.
- While Edit Mode is open the moves and stretch stay on, so the block keeps its place in the row there (the user's choice: taking them off made the block pop out to a spot that was hard to grab). Edit Mode still saves only what the player moves: a bar they drag is saved where they drop it and leaves Blizzard's arrangement, which the moves apply to. On leaving Edit Mode the art is measured again.
- In combat every change (moves, stretch, the block's own place) waits for `PLAYER_REGEN_ENABLED`: protected frames can't be moved then.
- Taint log: after the `UpdateDividers` fix the log showed the addon tainting only its own objects (its colors, its Edit Mode box). What stays with taint logging on is the client's wrapper bug: the XP bar's `SetPoint` wrapper at EditModeManager.lua:710 failing while calling the addon's hook, four times during `/reload` and once when Edit Mode opened.

## Floating
The user's design. The block's place is its slot by the micro menu, wherever the player puts the micro menu: the slot belongs to the micro menu as the bags bar does in Blizzard's layout, so moving the whole bottom bar takes the block along, and the bags bar makes room for it there too. It stands on a spot of its own only when the player drags it there in Edit Mode.
- The slot is on the micro menu's right side, joined as the bags bar is. It stays on the screen: when the block, or the bags bar making room for it, would reach past the right edge, it stands on the micro menu's left side (joined the same way, mirrored) unless the action bar hangs there or it wouldn't fit either, and else just above the micro menu's right end. Only on the right side does the bar make room. Why: with the micro menu in the screen's bottom-right corner, the block hung past the screen's edge (a player's report).
- Rejected (1.3.0 to 1.4.2): a moved micro menu made the block float beside it on a free side with nothing making room, and the block let go of the micro menu while the player moved it; after moving the whole bottom bar it couldn't be put back in its place, and Reset To Default Position sent it to the side the anchors said was free. The user asked for the slot instead.
- No micro menu on screen (another addon replacing the bars): the block stands where it stands in the gamepad interface.
- A saved spot: the block stands there, its center at the saved point.
- The block is clamped to the screen by its own size (`SetClampedToScreen`, no clamp insets), as Edit Mode clamps the game's bars (`clampedToScreen` in `EditModeSystemTemplate`); its frame art may reach past the screen's edge like theirs. Counting the frame art too (1.3.0 to 1.4.0) pushed the block about 3 units up in the row at the screen's bottom, where the bags bar's art also reaches below the edge.
- In Edit Mode the block stays where it is and shows as Edit Mode shows the game's bars: Blizzard's nine-slice box (`NineSliceCodeTemplate`, `NineSliceUtil.ApplyLayout`), blue (`editmode-actionbar-highlight`), yellow while selected or dragged (`editmode-actionbar-selected`), one frame level above Edit Mode's own boxes (read from `MicroMenuContainer.Selection`) so it is easy to grab. Mouse over shows its name and `HUD_EDIT_MODE_INSTRUCTIONS_CLICK_TO_EDIT`. Edit Mode's box layout is local in `EditModeSystemTemplates.lua` (`EditModeSystemSelectionLayout`), so its values are copied into the addon.
- A click selects it and opens its settings (the user's design), built like the game's settings dialog (`EditModeSystemSettingsDialog`, whose own template hooks into Edit Mode, so it isn't used): `DialogBorderTranslucentTemplate`, the title in `GameFontHighlightLarge`, `UIPanelCloseButton`, a slider row like `EditModeSettingSliderTemplate` (`MinimalSliderWithSteppersTemplate`, a percentage on the right), `UIPanelButtonTemplate` buttons and the divider, with the game's words. Its measures are read from the game's dialog, which always exists: strata and level, padding (`widthPadding`, `heightPadding`), the title's font object and place, spacing, the Revert Changes button and the divider; Blizzard's values from `EditModeDialogs.xml` only if a piece is missing. The slider row and the wide button come from templates the game makes only for its own bars, so their sizes are Blizzard's values from `EditModeTemplates.xml` and `EditModeDialogs.xml`. It opens at the bags bar's settings dialog anchor (`GetSettingsDialogAnchor`) and can be dragged.
- One thing is selected at a time, as in the game (the user's rule): selecting the block first clears Edit Mode's selection with `EditModeManagerFrame:ClearSelectedSystem()`, which closes the game's dialog. Called from outside Blizzard's code out of combat, that function runs its clearing through a secure delegate (`CreateSecureDelegate`: secure execution taint), so it stays Blizzard's own; the addon never calls it in combat, and Edit Mode can't be open then anyway. Selecting one of the game's bars (`SelectSystem`), Edit Mode clearing its selection (`ClearSelectedSystem`, both hooked) or leaving Edit Mode deselects the block and closes its dialog.
- Keys, like the game's dialog (the user's choice): closing the dialog plays `SOUNDKIT.IG_MAINMENU_CLOSE` (`EditModeBaseDialogMixin`'s OnHide). While open it takes the keyboard: Escape closes it; the arrow keys move the block a step in its own units, ten with Shift (`EditModeSystemMixin:ProcessMovementKey`), and a block in its slot then stands on its own a step away; every other key goes on to the game (`SetPropagateKeyboardInput`, never in combat).
  - Size (`HUD_EDIT_MODE_SETTING_BAGS_SIZE`): the bags bar's Size slider (range and step read from `EditModeSettingDisplayInfoManager`, 75 to 200 in steps of 5 as a fallback), as a percentage of the bags bar's size. 100% is the default, so the block matches the bags bar unless the player changes it. In the row the bags bar joins a resized block as it joined the micro menu, and the row grows by it.
  - Revert Changes: back to the spot and size the block had when Edit Mode opened or the layout was last saved (`EditMode.SavedLayouts`), enabled only when something changed, like the game's button (the user asked for it; after leaving and reopening Edit Mode there is nothing to revert, as in the game).
- Edit Mode's Revert All Changes, and Exit or Switch in its unsaved-changes dialog (`EditModeUnsavedChangesDialog.ProceedButton`), put the block back the same way (the user's choice). Edit Mode runs `RevertAllChanges` on every exit, saved or not, so the block follows those buttons' clicks instead (`HookScript("PreClick")`, before the click leaves Edit Mode). The game's buttons only know the game's bars: with only the block changed, Revert All Changes stays disabled and leaving asks nothing, so the block's changes stay; its own Revert Changes covers that. Making the game count the block's changes would mean writing Edit Mode's state, which the addon never does.
  - Reset To Default Position: back in its slot by the micro menu, wherever that stands; the size stays, as with the game's button. Enabled only when the block has a saved spot.
- The player drags it in Edit Mode in both interfaces (the user's choice), each with a spot of its own: the game keeps an Edit Mode layout per interface. In the gamepad interface its home is where it stood there before, between the XP bar and the gamepad buttons (the user's choice); dropped within a slot's size of it, or reset, it goes back there. With mouse and keyboard, dropped within a slot's size of its slot (wherever the micro menu stands, on the side the slot is on), it goes back in and the spot is forgotten; dropped anywhere else, it floats there and the spot is saved. Nothing re-places it while it is being dragged.
- The micro menu is watched from login (`SetPoint`/`ClearAllPoints` hooks) like the bags bar, so moving it re-places the block.

## Saved data
- `AmILaggingDB` (per account, `## SavedVariables` in both TOCs): `format` (1); once the player dragged the block, `spot` (mouse and keyboard) and `gamepadSpot` (added without a new format), the block's center `{ x, y }` in UIParent units from the screen's bottom left; once they changed its size, `size`, the percentage, shared by both interfaces.
- `NormalizeSaved` runs at `PLAYER_LOGIN`: a spot stays only when both numbers are finite, a size only inside the slider's range and when it isn't 100.

## Never
- Never save or change an Edit Mode layout (`C_EditMode.SaveLayouts` and the like): the user rejected it.
- Never move Blizzard frames other than the roots of the bottom row, the bars stacked on it and the bags bar, as described above.
- Save nothing but the block's spot and size (the user's choice). Nothing else the addon does may outlive it.
