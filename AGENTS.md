# Am I Lagging?

Rules for this addon. The shared rules are in `../AGENTS.md`.

A bag-slot-sized block on the bottom bar, in a bar of its own, that always shows the framerate and the world latency, numbers the game menu button shows only in its tooltip. It moves with the micro menu, and players can put it anywhere in Edit Mode. Agreed with the user.

The name is "Am I Lagging?" (title case; `ADDON_TITLE` in the code, also the tooltip title and the start of chat lines). CurseForge project ID: 1720989. Folder, repo and packages are `AmILagging`, since "?" doesn't belong in file names. The package ships `AmILagging_Camelot.toc` as an exact copy of `AmILagging.toc` (a test checks it): versions 0.8.0 to 1.1.2 shipped only a `_Camelot` TOC, which the game reads before the plain one. A player who unzips an update over such a folder gets the stale file replaced; without the copy, the game would keep reading the old TOC (old version in the addon list, and out of date at the next `## Interface`). CurseForge marks files with both TOCs compatible (Salve does the same). Keep both; never drop the copy. Nothing else from older versions can interfere: no version had SavedVariables, every version loaded only `AmILagging.lua`, and the CurseForge-built 1.1.4's extra files (`AGENTS.md`, `CLAUDE.md`, `CHANGES.txt`, `Logo/`) are never loaded. Renamed from "Performance Block" on 2026-10-01: the name says what the player wants to know. CurseForge search terms (fps, latency, ping) go in the summary, since the name has none. The `.toc` has `## Category: Performance` (the addon list groups by it and its search box matches it). The package ships the MIT license, like Just the Trees (user's choice, 2026-10-01).

## Look

- A bar of its own between the micro menu and the bags bar: one slot in the game's bar frame art, joined to the micro menu where the bags bar hung, with the bags bar joined to it the same way. The user chose this on 2026-10-05, so the block no longer disappears with the bags bar (gamepad interface, addons that hide the bags bar). From 2026-10-01 to then it was the bags bar's first slot; before that (0.5–0.6) it was this same bar of its own. It is a pitch black, fully opaque face inside the game's slot frame (the game's empty-slot background was see-through; the user chose solid black, 2026-10-01).
- It is part of the whole, not pixel-matched: the art and size are read at login (and after Edit Mode) from the frames around it, with Blizzard's XML values only as fallbacks (also when a frame reports no size yet): the bar frame art and how far it reaches past the slot from `BagsBar.BorderArt`, how far the micro menu's frame art reaches past its right end from `MicroMenu.BorderArt`, the slot size and plain gray frame art from `CharacterReagentBag0Slot` (regular bag slots wear a gold frame, which made the block stand out). It takes the bags bar's scale (its Edit Mode Size) times its own Size setting (see Floating), and the bags bar's strata and frame level. No empty-slot picture or background art: just black behind the numbers (2026-10-01).
- Numbers only, no labels: FPS on top in white, world latency below in its color, both 15 px, centered horizontally on the slot frame art. A line runs across the frame art's center (32 px wide, fading at both ends), colored by home latency with the same green/yellow/red rule (the user's choice after trying it in game, 1.1.0, 2026-10-01; it was gold before). This font's figures are old style (6 and 8 rise; 3, 4, 5, 7 and 9 drop), so each number is placed by the band from its highest to its lowest possible figure (em ratios measured from Skurri in game), centered in its half of the slot: the same gap to the line as to the slot's gray inner edge, whatever the digits. The user asked for airiness: no digit may touch the line or the border. The font is the game's own heavy number font, read from `NumberFont_Outline_Huge` (Skurri for Latin alphabets) with a normal outline, one text line per number; `STANDARD_TEXT_FONT` if that font object is missing. The user wants a font built into the game, not a bundled one, and no faux-bold tricks (drawing copies was rejected as hacky).
- The background is uniform pitch black.
- World latency only on the face: it is the delay felt in combat and movement. Home latency (chat, mail, auction house) is in the tooltip. The user chose this after it was explained; readability at true size (45 px) was the reason.
- A number wider than the slot less a 6.5 px margin each side (four-digit latency) shrinks to fit.
- Only the latency number changes color, with the game menu button's rule: green up to 300 ms, yellow over 300, red over 600. FPS stays white. (The game menu button colors by the worse of home and world; the block colors the number it shows.)
- The numbers update once a second while the block is on screen; a number that didn't change is left alone.
- Tooltip: the title, an empty line (as the game menu tooltip has), then the game's own framerate and latency lines, FPS first to match the face (`MAINMENUBAR_FPS_LABEL`, then `MAINMENUBAR_LATENCY_LABEL` with home and world), then `v<VERSION>`. Under the framerate, "Limited by: CPU" or "Limited by: GPU" from `IsCpuBound()`, as the game's Ctrl+R counter tells it; left out when it returns nil. The game can't report GPU load; this line is what it offers (the user chose it, 2026-10-01). The tooltip stays current while open through the block's `UpdateTooltip`, which the game's tooltip calls on its own timer, as the game menu tooltip stays current.

## Chat

- Every line starts with "Am I Lagging?:" in gold (`NORMAL_FONT_COLOR`), as in Just the Trees.
- The addon writes only when something stopped working: what stopped in red (`RED_FONT_COLOR`), then what the player can do. The user chose no other messages (no login line, no slash command, no lag warning; 2026-10-01).

## Errors

- At login the addon checks the piece it can't do without (the micro menu it stands by). If it is missing, it says so in chat and does nothing else.
- Making room runs inside the game's own code, right after Blizzard moves or resizes a frame, so every hook and callback runs through `Guarded` (`xpcall` with the game's `CallErrorHandler`). An error never breaks the code that called it. The first error is reported through the game's error handler and said once in chat; the addon then puts the bar back the way the game set it (block hidden, no moves, no stretch) and keeps it so until /reload. If even that fails, it leaves the bar alone.
- If reading the numbers fails, the error is reported once, the numbers are cleared (old numbers would mislead), the updates stop and chat says so.

## Making room (agreed with the user)

The addon makes room for itself, and removing it leaves no trace.
- The block is its own frame, a child of UIParent (it hides with the interface, Alt+Z), anchored to `MicroMenuContainer` exactly as Blizzard anchored the bags bar there (its point, the micro menu's point and the offsets, read from the bags bar's own anchor). When the bags bar hangs elsewhere, the block joins the micro menu as Blizzard's layout joins the bags (`BAGS_ANCHOR_*` from Camelot's preset constants). It joins no Blizzard list.
- The bags bar, when it hangs off the micro menu's right side, moves right to join the block as it joined the micro menu: with the same overlap of frame art, so it stands the join plus the block's reach less the micro menu's reach after the block (the 0.5–0.6 join). A bags bar hung elsewhere is left where it is.
- The block stays when the bags bar is hidden, however it was hidden. Without the micro menu on screen (shown, and every frame above it up to UIParent shown: another addon may hide it by parenting it to a hidden frame), as when another addon replaces the game's bars, the block floats (see Floating).
- In the gamepad interface (`C_InputInterfaceStyle`) the game hides the row (micro menu, bags bar, action bar). The block then stands on its own, centered on the screen and between the XP bar's top and the gamepad buttons' frame (`GamepadMainActionBarFrame`) bottom, where the user marked it on a screenshot (2026-10-05); without that frame, just above the XP bar. Nothing moves there. The switch is followed through `INPUT_DEVICE_INTERFACE_TRANSITION` and the micro menu's, gamepad frame's and XP bar's `OnShow`/`OnHide`; the XP bar is watched from login for where it stands.
- Edit Mode has no way for an addon to add a system (a fixed game list, layouts saved on the server), and in Camelot the row sits at a fixed offset (`MICRO_MENU_ANCHOR_OFFSET_X`), so nothing in Blizzard's layout recenters a wider row. While the block is in its slot and the micro menu where Blizzard's layout puts it, the whole row moves left by half the growth (the slot and the join to the bags, at the bags bar's scale, in UIParent units). What the row hangs off depends on the layout (in a saved layout the action bar hangs off the micro menu; Edit Mode places bars in their default position on the screen itself), so the addon follows the anchor chains of `MainActionBar` and `MicroMenuContainer` to the frames that hang off the screen and moves each such root once. Where the player put the micro menu, it stays where they dropped it and the row grows to the right (the stacked bars, the XP bar stretch and the bags bar move as below; only the roots don't). The action bar is part of the row only while it is in its default position (Edit Mode's `IsInDefaultPosition`): a player who moved it took it, and the bars Blizzard stacks on it, out of the row, so neither it nor they move or stretch (released versions up to 1.2.1 nudged a moved action bar half a slot; found in the 2026-10-06 audit).
- The bars above the row come from Blizzard's own list of bottom bars (`EditModeUtil:GetBottomActionBars()`, without `MainActionBar`): the XP bars, the action bars stacked above them (`MultiBarBottomLeft`, `MultiBarBottomRight`, `StanceBar`, `PetActionBar`, `PossessActionBar`) and the vehicle exit button. Camelot stacks them on `MainActionBar` by their left edge (`ACTION_BARS_RELATIVE_TO_BASE_POSITIONING`), so they move with the row and line up with its left end. Only bars anchored to `MainActionBar` are touched; a bar the player moved elsewhere is left as it is.
  - The XP bar containers (the bars with `ResizeContainerBars`, `UpdateDividers` and `GetExpectedSegments`) stretch by the row's growth to reach its right end, with Blizzard's own methods, as its Size setting does. `hooksecurefunc`s on their `SetSize`/`SetWidth` keep the stretch when Blizzard resizes them, and on `SetPoint` notice them moving onto or off the row. A container is only resized when its width has to change.
  - The other bars are fixed buttons and cannot stretch, so they move right by half the growth to stay centered over the row.
  - They are watched from login: Edit Mode first parks them at the screen's top left and stacks them on the action bar a moment later.
- Moves are applied in `hooksecurefunc`s on `SetPoint` and `ClearAllPoints` of each moved frame, each time Blizzard anchors it, from the points Blizzard set. Each point is remembered and moved on its own: Edit Mode gives a frame a second point when it is snapped to two others, and sets the two one after the other. The moves use Edit Mode's plain `SetPointBase`: its replaced `SetPoint` and `ClearAllPoints` also change snapping and flag anchor changes, which the addon must not do, and the plain original never reaches the addon's own hooks. A point is only set when its offset has to change, and remembered as moved only once the move worked. Offsets and widths are converted with effective scales, since frames can be scaled apart.
- Edit Mode drags: the client moves a bar the player drags itself (`StartMoving`, `StopMovingOrSizing`), replacing its points without `SetPoint`, so the hooks don't see it; after the drop Edit Mode sets the point again on UIParent and only then marks the bar as moved (`UpdateSystemAnchorInfo`). So a bar in the player's hand (Edit Mode's `isDragging`) is never moved; before each move the remembered points are checked against the frame's own (a point the frame no longer has is forgotten, never put back); and the layout runs again once Edit Mode is done with a moved bar (`OnSystemPositionChange` hooked). Before 2026-10-06 the addon could put back a point the game had replaced, nudge a dropped micro menu or bags bar, and move a bar in the player's hand; the user saw Edit Mode lose the micro menu's edges while dragging it ("attempt to perform arithmetic on local 'left'" at EditModeSystemTemplates.lua:607), proven possible in the stand-in, not proven to be that error's cause.
- The bags bar is watched from login like the other moved frames (`SetPoint`/`ClearAllPoints` hooks): where Blizzard hangs it decides where the block stands. `OnShow`/`OnHide` also run when a frame above a hooked frame is shown or hidden; hiding the whole interface (Alt+Z) hides only UIParent and changes nothing.
- While Edit Mode is open the moves and stretch stay on, so the block keeps its place in the row there (the user's choice, 2026-10-06: taking them off made the block pop out to a spot that was hard to grab). Edit Mode still saves only what the player moves: a bar they drag is saved where they drop it, and the moves only apply to bars still in Blizzard's arrangement (a dragged bar leaves it). On leaving Edit Mode the art is measured again.
- In combat every change waits for `PLAYER_REGEN_ENABLED`: protected frames can't be moved then.
- Taint: the block is in no Blizzard list, so Blizzard's bags bar layout runs clean. The moves still run from the addon's hooks (all wait for the end of combat).
- With taint logging on (`taintLog`), the game sometimes fails inside the `hooksecurefunc` wrappers, here the XP bar's `SetPoint` ("attempt to call a nil value" at EditModeManager.lua:710), at load and in play, in any addon. It never happened with taint logging off, so it is the client's and the hooks stay (see the shared rules' taint check). On 2026-10-06 the same wording, with a Blizzard line on top, also came from a plain call nothing hooks (`BottomManagedFrameContainer:ClearAllPoints` at UIParentPanelManager.lua:813, in Edit Mode and at logout) and from the addon's `ClearSelectedSystem` hook (EditModeManager.lua:1656, leaving Edit Mode), all with taint logging on (the user confirmed); the shared rules now say so.

## Floating (the user's design, 2026-10-06)

The block's place is its slot by the micro menu, wherever the player puts the micro menu (the user's choice, 2026-10-06: the slot belongs to the micro menu, as the bags bar does in Blizzard's layout, so moving the whole bottom bar takes the block along, and the bags bar makes room for it there too). It stands on a spot of its own only when the player drags it there in Edit Mode.
- The slot is on the micro menu's right side, joined as the bags bar is. It stays on the screen: when the block, or the bags bar making room for it, would reach past the right edge, it stands on the micro menu's left side (joined the same way, mirrored) unless the action bar hangs there or it wouldn't fit either, and else just above the micro menu's right end. Only on the right side does the bar make room. Why: with the micro menu moved to the screen's bottom-right corner, the block on its right hung past the screen's edge (a player's report, 2026-10-03 to 06).
- Before 1.5.0 (1.3.0 to 1.4.2) a moved micro menu made the block float beside it on a free side with nothing making room, and in 1.4.2 the block let go of the micro menu while the player moved it (the user's rule then); after moving the whole bottom bar it couldn't be put back in its place, and Reset To Default Position sent it to the side the anchors said was free. The user asked for the slot instead.
- No micro menu on screen (another addon replacing the bars): the block stands where it stands in the gamepad interface, centered between the XP bar and the gamepad buttons' place.
- A saved spot: the block stands there, its center at the saved point.
- The block is clamped to the screen by its own size (`SetClampedToScreen`, no clamp insets), as Edit Mode clamps the game's bars (`clampedToScreen` in `EditModeSystemTemplate`); its frame art may reach past the screen's edge like theirs. 1.3.0 to 1.4.0 counted the frame art too: in the row at the screen's bottom, where the bags bar's art also reaches below the edge, that pushed the block up about 3 units (the user's screenshot, 2026-10-06).
- In Edit Mode the block stays where it is and shows as Edit Mode shows the game's bars: Blizzard's nine-slice box (`NineSliceCodeTemplate`, `NineSliceUtil.ApplyLayout`), blue (`editmode-actionbar-highlight`), yellow while selected or dragged (`editmode-actionbar-selected`), one frame level above Edit Mode's own boxes (read from `MicroMenuContainer.Selection`) so it is easy to grab. Mouse over shows its name and `HUD_EDIT_MODE_INSTRUCTIONS_CLICK_TO_EDIT`. Edit Mode's box layout is local in `EditModeSystemTemplates.lua` (`EditModeSystemSelectionLayout`), so its values are copied into the addon.
- A click selects it and opens its settings, the user's design (2026-10-06), built like the game's settings dialog (`EditModeSystemSettingsDialog`, whose own template hooks into Edit Mode, so it isn't used): `DialogBorderTranslucentTemplate`, the title in `GameFontHighlightLarge`, `UIPanelCloseButton`, a slider row like `EditModeSettingSliderTemplate` (`MinimalSliderWithSteppersTemplate`, a percentage on the right), `UIPanelButtonTemplate` buttons and the divider, with the game's words. Its measures are read from the game's dialog, which always exists: strata and level, padding (`widthPadding`, `heightPadding`), the title's font object and place, spacing, the Revert Changes button and the divider; Blizzard's values from `EditModeDialogs.xml` only if a piece is missing. The slider row and the wide button come from templates the game only makes for its own bars, so their sizes are Blizzard's values from `EditModeTemplates.xml` and `EditModeDialogs.xml`. It opens at the bags bar's settings dialog anchor (`GetSettingsDialogAnchor`) and can be dragged. Only one thing is selected at a time, as in the game (the user's rule, 2026-10-06): selecting the block first clears Edit Mode's selection with `EditModeManagerFrame:ClearSelectedSystem()`, which closes the game's dialog. Called from outside Blizzard's code out of combat, that function runs its clearing through a secure delegate (`CreateSecureDelegate`: secure execution taint), so it stays Blizzard's own; the addon never calls it in combat, and Edit Mode can't be open then anyway. Selecting one of the game's bars (`SelectSystem`), Edit Mode clearing its selection (`ClearSelectedSystem`, both hooked) or leaving Edit Mode deselects the block and closes its dialog.
- Keys, like the game's dialog (the user's choice, 2026-10-06): closing the dialog plays `SOUNDKIT.IG_MAINMENU_CLOSE` (`EditModeBaseDialogMixin`'s OnHide). While it is open it takes the keyboard: Escape closes it; the arrow keys move the block a step in its own units, ten with Shift (`EditModeSystemMixin:ProcessMovementKey`), and a block in its slot then stands on its own a step away; every other key goes on to the game (`SetPropagateKeyboardInput`, never in combat).
  - Size (`HUD_EDIT_MODE_SETTING_BAGS_SIZE`): the bags bar's Size slider (range and step read from `EditModeSettingDisplayInfoManager`, 75 to 200 in steps of 5 as a fallback), as a percentage of the bags bar's size. 100% is the default, so the block always matches the bags bar unless the player changes it. In the row the bags bar joins a resized block as it joined the micro menu, and the row grows by it.
  - Revert Changes: back to the spot and size the block had when Edit Mode opened or the layout was last saved (`EditMode.SavedLayouts`), enabled only when something changed, like the game's button (the user asked for it; after leaving and reopening Edit Mode there is nothing to revert, as in the game).
- Edit Mode's Revert All Changes, and Exit or Switch in its unsaved-changes dialog (`EditModeUnsavedChangesDialog.ProceedButton`), put the block back the same way (the user's choice, 2026-10-06). Edit Mode runs `RevertAllChanges` on every exit, saved or not, so the block follows those buttons' clicks instead (`HookScript("PreClick")`, before the click leaves Edit Mode). The game's buttons only know the game's bars: with only the block changed, Revert All Changes stays disabled and leaving asks nothing, so the block's changes stay; its own Revert Changes covers that. Making the game count the block's changes would mean writing Edit Mode's state, which the addon never does.
  - Reset To Default Position: back in its slot by the micro menu, wherever that stands; the size stays, as with the game's button. Enabled only when the block has a saved spot.
- The player drags it in Edit Mode (not in the gamepad interface, where it keeps the gamepad spot). Dropped within a slot's size of its slot (wherever the micro menu stands, on the side the slot is on), it goes back in it and the spot is forgotten; dropped anywhere else, it floats there and the spot is saved. Nothing re-places it while it is being dragged.
- The micro menu is watched from login (`SetPoint`/`ClearAllPoints` hooks) like the bags bar, so moving it re-places the block.

## Saved data

- `AmILaggingDB` (per account, `## SavedVariables` in both TOCs): `format` (1); when the player dragged the block, `spot` = the block's center `{ x, y }` in UIParent units from the screen's bottom left; when they changed its size, `size` = the percentage.
- `NormalizeSaved` rebuilds it at `PLAYER_LOGIN` from those fields and drops everything else: a spot stays only when both numbers are finite, a size only inside the slider's range and when it isn't 100.

## Never

- Never save or change an Edit Mode layout (`C_EditMode.SaveLayouts` and the like). The user rejected it: removing the addon must leave the layout as it was.
- Never move Blizzard frames other than the roots of the bottom row, the bars stacked on it and the bags bar, as described above. The block joins no Blizzard list (taint).
- Save nothing but the block's spot and size (the user's choice, 2026-10-06; before then the addon saved nothing). Nothing else the addon does may outlive it.
